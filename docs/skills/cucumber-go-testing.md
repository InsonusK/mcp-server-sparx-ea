# Требования: качественные тесты на Go + Cucumber (godog)

> Черновик. Копим пункты по мере выработки на примере `client/eapx`.
> Потом отдельной задачей превратим в полноценный скилл.

## 1. Общая философия

- **Все тесты — Cucumber-сценарии** (godog). Плоских Go-тестов (`func TestXxx`) нет,
  кроме одного `TestFeatures` — раннера godog.
- Код, до которого **нельзя добраться через публичный API**, — удаляем, а не покрываем юнит-тестом
  (пример: nil-guard в приватной обёртке, у которой один дисциплинированный вызыватель).
- Не используем **баги/квирки нижележащих библиотек** как проверки.
  Тестируем поведение **своего** кода.
- Сценарий, который **нельзя выполнить сейчас** (нет фикстуры) → тег `@todo` + фильтр `~@todo`
  в раннере. Он не должен быть фейково-зелёным (godog `ErrSkip` в `go test` считается `pass`!).

## 2. Обобщённые компараторы (generic comparator steps)

- Ассерт-шаг **не делает ничего доменно-специфичного** — он сравнивает фактический результат
  с ожидаемыми данными, которые пришли **из feature-файла** (data table / параметр).
- Плохо (специфичный шаг, надо аудировать каждый):
  ```gherkin
  Then object 7 is a Goal named "Goal1"
  ```
- Хорошо (обобщённый компаратор, один на все сценарии):
  ```gherkin
  Then the result is exactly:
    | Object_ID | Name  | Object_Type | Note             |
    | 7         | Goal1 | Class       | Goal description |
  ```
  Код шага (~15 строк): заголовок таблицы = `rs.Columns`; строки таблицы = `rs.Rows`
  (как множества — см. п.6 про порядок). Такой шаг **структурно не может быть пустышкой**:
  он проверяет каждую ячейку таблицы.
- Итог: обобщённых шагов всего ~6–8 (open / run query / result-is-exactly / result-is-empty /
  query-fails-with / value-is-valid-utf8 / ...). Их аудируешь один раз. Вся конкретика — в `.feature`.

## 3. Конкретность проверок

- Не «получили какие-то объекты», а «открыли файл X, выполнили запрос Y, получили строку `A | B | C`».
- Ожидаемые значения — **в feature-файле** (data table / Scenario Outline), не захардкожены в коде шага.
- Считаем строки **в Go-коде шага** (`len(rs.Rows)`), не через `count(*)`.
- Структурные ответы (JSON) проверяем **демаршалингом в структуру**, не `strings.Contains` по тексту.
- Кодировку проверяем и по значению (`== "Цель"`), и по валидности (`utf8.ValidString`),
  желательно и по байтам для одного якорного значения.

## 4. Логирование шагов

- Каждый шаг, у которого есть метод, **логирует что сделал и что увидел**. Общий хелпер `logf`
  пишет **прямо в stdout** (`fmt.Printf`), а не через `t.Log`:
  - строка встаёт **inline** в дерево godog pretty, рядом со своим шагом;
  - VS Code привязывает её к запущенному сценарию, а не к `testingt.go` внутри godog
    (через `godog.T(ctx).Logf` строка приезжает с локацией `testingt.go:NN` и «теряется»).
- Первый аргумент функции шага — `ctx context.Context` (пока не используется, оставлен на будущее).
- Формат: коротко, «действие → наблюдаемый результат».
  `connected to "testdata/TestProject.eapx"`,
  `query "select ..." → 16 row(s), columns [Object_ID Name]`.
- **Когда логи видно** (стандартное поведение `go test`):
  - на **упавшем** сценарии — всегда;
  - на зелёном прогоне — **только с `go test -v`** (без `-v` Go прячет вывод прошедших тестов).
    В репо это включено: `.vscode/settings.json` → `"go.testFlags": ["-v"]`.
  - Путь конкретного сценария в терминале: `go test ./client/eapx/test/ -v -run 'TestFeatures/<name>'`.
- Цель: при падении сценария виден весь путь, а не только финальный assert.

## 5. Организация step-определений

- Файлы шагов разбиваем **по доменному понятию**: `connection_steps_test.go`, `query_steps_test.go`,
  `result_steps_test.go`, ... (в этом домене они совпадают с фазами Given/When/Then — это ок).
- godog матчит шаг по тексту **независимо** от `Given`/`When`/`Then`/`And` — одно определение
  работает во всех фазах.
- **Не** нумеруем шаги (`G1`, `W1`) и не помечаем «общий/локальный» в тексте feature —
  Gherkin остаётся человекочитаемым доменным языком.
- Переиспользуемость — через **параметризацию** (`I run the query {string}` на все запросы),
  не через ручную дедупликацию/каталог.
- Уникальный для одного feature шаг — в файле `{feature}_steps_test.go`; общий — в файле по понятию.
- Индекс всех шагов при необходимости **генерируем**: `godog.Options{ShowStepDefinitions: true}`
  (за env-флагом), не ведём руками.

## 6. Порядок строк и подмножество SQL

- В результате `SELECT` строки идут в **порядке хранения**, не по ID и не по какому-либо полю.
  → Многострочные ассерты сравниваем **как множества**, либо берём ровно одну строку через `WHERE ... = N`.
- Тесты используют только тот SQL, который реально поддерживает нижележащий движок.
  Для mdbtools (текущий бэкенд): `SELECT cols FROM table [WHERE simple = / <> / LIKE / AND / OR]`.
  **Не поддерживаются**: `ORDER BY`, `LIMIT`, `IN (...)`, `count(*)` с `WHERE`, JOIN.

## 7. Раскладка

Два варианта, оба валидны:

**А. Плоский тест-пакет** (`client/eapx`): всё в `client/eapx/test/`, файлы по доменному понятию,
общий `world` в `world_test.go`.

**Б. С подпакетом `common/`** (`internal/service/sparx`) — когда step-файлов много:
```
internal/service/sparx/features/           одна *.feature на операцию (create/edit/read/delete)
internal/service/sparx/test/
  common/                                  package common (обычный, не _test)
    world.go     — World (экспортируемый) + reset + Logf + FixturePath
                 + plumbing-шаги (загрузка модели/рабочей копии, save, reload)
                 + generic-компараторы (ToRows, MatchTable, "the X is:", "... include:")
  suite_test.go                            TestFeatures + сборка
  <operation>_steps_test.go                ТОЛЬКО action-шаги ("I create", "I relate", "I add …")
  testdata/
  tmp/                                     сохранённые рабочие копии (gitignore)
```
- `common/` — обычный пакет с экспортируемым `World`; action-шаги в `sparxtest` берут `*common.World`.
- Граница: `common/` = plumbing + assertions (что переиспользуется); `test/*_steps_test.go` = действия
  (что специфично для операции). Читателю сразу видно: assertion → в `common/`, действие → рядом с feature.

Общее для обоих: фикстуры в `testdata/` (не ссылки на `example/`); раннер
`Options.Paths=["../features"]`, `Tags="~@todo"`, `Strict=true`, `TestingT=t`; env `GODOG_STEPS=1` → каталог шагов.

## 7a. Тесты, которые пишут файл (мутации)

- Рабочая копия загружается в память из `testdata/`, правится, сохраняется в `tmp/<output>.xml`.
  **Файл фикстуры никогда не перезаписывается.**
- `tmp/` в `.gitignore`, чистится в начале прогона (`os.RemoveAll` в `TestFeatures`), **остаётся после** —
  пользователь открывает в целевом приложении и проверяет/импортирует.
- **Каждый мутационный сценарий явно объявляет** источник, выходной файл и (для EA) имя root-пакета:
  ```gherkin
  Given the working model:
    | source | TestProject.xml    |
    | output | element_create.xml |
    | root   | element create     |
  ```
  Свой root-name на файл (со свежим GUID) → все выходные файлы можно импортировать в один проект
  рядом друг с другом и сравнить с оригиналом.
- Ассерты — через **reload**: `after reload the element "…" is:` переоткрывает сохранённый файл, т.е.
  проверка идёт по реальному round-trip, а не по объекту в памяти.
- **Один output-файл на сценарий** (детерминированные проверки); не аккумулируем изменения в один
  файл, не делаем merge пакетов между сценариями. `Given the working model` — **в самом сценарии**,
  не в `Background` (иначе несколько сценариев пишут в один файл и остаётся состояние последнего).
  Валидационный (падающий) сценарий тоже получает свой `output` (`..._bad.xml`, `..._refused.xml`) —
  чтобы файл успешного сценария не затирался частичной подготовкой упавшего.
- Общие подготовительные элементы (helper-ы для проверки связей) создаёт **один составной шаг**,
  вызываемый в каждом сценарии, а не отдельный сценарий-предок.

## 8. Конкретные типы сценариев

- **Конкуренция:** тест обязан **падать при снятии синхронизации**. Горутины запрашивают
  **разные** данные и каждая сверяет **полную известную строку** — при гонке содержимое
  перемешается/поломается. `-race` обязателен, но сам по себе гонку в C-библиотеке не ловит.
- **In-process / read-only:** слабо «не пишет временных файлов». Сильнее —
  «файл `.eapx` на диске **байт-в-байт (size+mtime) не изменился** после N запросов».
- **Архитектурные концерны** — отдельные `.feature`, отдельно от бизнес-сценариев.

## 9. Связь с другими скилами

- `solution-conformance-testing` — Cucumber на все тест-кейсы, 4 make-цели, отчёт.
- `code-coverage` — 80%+.
