# Требования: качественные тесты на Go + Cucumber (godog)

> Черновик. Копим пункты по мере выработки на примере `client/eapx`.
> Потом отдельной задачей превратим в полноценный скилл.

## 1. Общая философия

- **Все тесты — Cucumber-сценарии** (godog). Плоских Go-тестов (`func TestXxx`) нет.
- Код, до которого **нельзя добраться через публичный API**, — удаляем, а не покрываем юнит-тестом
  (пример: nil-guard в приватной обёртке, у которой один дисциплинированный вызыватель).
- Не используем **баги/квирки нижележащих библиотек** как проверки.
  Пример: `select count(*)` в mdbtools сломан с `WHERE` — не тестируем через него.
  Тестируем поведение **своего** кода.
- Сценарий, который **нельзя выполнить сейчас** (нет фикстуры) → тег `@todo` + фильтр `~@todo`
  в раннере. Он не должен быть фейково-зелёным (godog `ErrSkip` в `go test` считается `pass`!).

## 2. Конкретность проверок

- Не «получили какие-то объекты», а «открыли файл X, выполнили запрос Y, получили строку `A | B | C`».
- Ожидаемые значения — **в feature-файле** (data table / Scenario Outline), а не захардкожены в коде шага.
- Ассерт-шаги — **тонкие обобщённые компараторы**: сравнивают результат с тем, что пришло из feature.
  Такой шаг структурно не может быть «пустышкой».
- Для многострочных/многоколоночных результатов — **data table** (`*godog.Table`):
  ```gherkin
  Then the result set is exactly:
    | Object_ID | Name  | Object_Type |
    | 7         | Goal1 | Class       |
  ```
- Считаем строки **в Go-коде шага** (`len(rs.Rows)`), не через `count(*)`.
- Структурные ответы (JSON) проверяем **демаршалингом в структуру**, не `strings.Contains` по сериализованному тексту.

## 3. Логирование шагов

- Каждый шаг, у которого есть метод, **логирует что сделал и что увидел** через `godog.T(ctx).Logf(...)`.
  Первый аргумент функции шага — `ctx context.Context`.
- Формат: коротко, «действие → наблюдаемый результат».
  Пример: `opened testdata/TestProject.eapx → connection ok`,
  `query "select ..." → 16 rows, columns [Object_ID Name]`.
- Цель: при падении сценария сразу виден весь путь, а не только финальный assert.

## 4. Организация step-определений

- Файлы шагов разбиваем **по доменному понятию**, не по ключевому слову Given/When/Then.
  (godog матчит шаг по тексту независимо от `Given`/`When`/`Then`/`And` — ключевое слово это просто проза.)
  Пример: `connection_steps_test.go`, `query_steps_test.go`, `result_steps_test.go`.
- **Не** нумеруем шаги (`G1`, `W1`) и не помечаем «общий/локальный» в тексте feature —
  Gherkin остаётся человекочитаемым доменным языком.
- Переиспользуемость шага — через **параметризацию** (один `I run the query {string}` на все запросы),
  а не через ручную дедупликацию и каталог.
- Число определений шагов держим маленьким: в домене мало глаголов (open / query / close / assert).
- Уникальный для одного feature шаг — в файле рядом (`{feature}_steps_test.go`), общий — в файле по понятию.
- Индекс всех шагов при необходимости **генерируем**: `godog.Options{ShowStepDefinitions: true}`
  (за env-флагом), не ведём руками.

## 5. Раскладка (для `client/eapx`)

```
client/eapx/features/            *.feature (остаются здесь)
client/eapx/test/                package eapxtest — чёрный ящик, импортирует client/eapx
  testdata/                      копии *.eapx фикстур (не ссылки на общий example/)
  suite_test.go                  TestFeatures + сборка InitializeScenario
  world_test.go                  общий world + reset + хелперы
  <concept>_steps_test.go        шаги по доменному понятию
  <feature>_steps_test.go        шаги уникальные для одного feature
```

- Один плоский тест-пакет (не подпакеты `common/` — иначе `world` пришлось бы экспортировать
  и усложнять регистрацию).
- Фикстуры — в `testdata/` тест-пакета. Тест не зависит от каталога `example/`.
- Раннер godog: `Options.Paths = ["../features"]`, `Tags = "~@todo"`, `Strict = true`, `TestingT = t`.

## 6. Конкретные типы сценариев

- **Конкуренция:** тест обязан **падать при снятии синхронизации**. Значит горутины запрашивают
  **разные** данные и каждая сверяет **полную известную строку** — при гонке содержимое
  перемешается/поломается. Прогон под `-race` обязателен, но сам по себе он гонку в C-библиотеке
  не ловит.
- **«Не пишет временных файлов»:** слабая проверка (libmdb и так не пишет). Сильнее —
  «файл `.eapx` на диске **байт-в-байт не изменился** после N запросов» (реальное доказательство
  read-only). Плюс снапшот `$TMPDIR`.
- **Архитектурные концерны** — отдельные `.feature`, отдельно от бизнес-сценариев.
